# 构思：把「想清楚」和「去做」接到一起

> 这是一份完整的构思，不是实现说明。实现见 `../README.md` 与 `../SKILL.md`。
> 文末有一组待验证的问题——**如果你是被请来审这份东西的，直接跳到第 9 节。**

## 0. 一句话

现有产品把「聊天」和「干活」合并了，但都只合了壳：一个 App 里放几个入口，或者干脆只有一套内核。
**真正没人解决的是两边的「交接」**——信息在窗口之间搬运时会丢，而丢了没人知道。

这套东西不重新造架构，只做一件小事：**让每一次交接都丢不了信息，也发不了假信号。**

## 1. 起点

问题最初长这样：能不能把官方的 chat-demo 做成桌面客户端的右栏插件？

查完发现：chat-demo 是纯前端聊天样例，**没有执行层**。它的「联网搜索」是服务端替它跑的，客户端只负责渲染。
把它搬进右栏，等于在一个能干活的环境里再放一个只能聊天的窗口——重复建设。

于是问题变成真的问题：**会聊天的和会干活的，怎么合到一起。**

## 2. 现状：两种合并，都在回避交接

| 层次 | 做法 | 谁在做 | 结果 |
|---|---|---|---|
| **壳合并** | 一个 App 里放多个视图，额度合并 | ChatGPT（Chat / Work / Codex） | 还是得自己选「现在用哪个我」 |
| **内核合并** | 只有一套循环，聊天也走执行系统 | DSH 这类本地工具 | 永远在执行模式：吵、急、显得浅 |
| **意图合并** | 系统自己判断这句要「想透」还是「立刻做」 | **没人做到** | —— |

补充两个事实：

- ChatGPT 的三个入口**历史是分开的**，合的是外壳和额度；
- 云端执行（Codex Cloud 之类）跑在隔离容器里，**看不到本地文件**，只认你推到 GitHub 的那份仓库。

所以「执行放在哪」和「文件在哪」是两件事。合并得再漂亮，文件不在执行者手边，交接照样要人搬。

## 3. 为什么交接是唯一难点

五种崩法，每一种都能单独毁掉「流畅」：

| 崩法 | 具体 |
|---|---|
| 上下文搬不动 | 你说过「这个方案不行」，对面看不到，于是照着旧想法干 |
| 状态不对等 | 聊天侧不知道执行侧改了什么；执行侧不知道你想清楚了什么 |
| 时机判断错 | 什么时候该交给执行侧？判断错两次，用户就不信这个切换了 |
| 回来不连续 | 执行完回到对话，历史里多了一堆命令输出。折叠、摘要、还是删？ |
| 中断不可续 | 做到一半失败，是重说一遍，还是能接上？ |

现在的产品只有两条**绕过**路线，没有一条解决它：

- **共享工作区**：交接靠文件，不靠对话（改代码的场景成立，纯讨论接不上）；
- **共享会话**：根本不交接，同一个 agent 一路干到底（对话会变吵变贵）。

## 4. 我们选的路：结果导向

用户要的是结果，不是过程。所以优先级整个翻过来：

| 过程导向 | 结果导向 |
|---|---|
| 先写计划书：目标、约束、不做什么 | 先定**什么算完成**：跑通哪条命令、输出长什么样 |
| 想得越深越好 | 想到能定标准就够，多想的都是浪费 |
| 交接要顺，不能丢上下文 | 交接不重要，**结果可验证就行**，丢了重跑 |
| 一次做对 | 快速试、错了就退 |

由此得到三条：

1. **验收命令比计划书值钱**。一条 `node check.mjs` 同时是目标、交接物和停止条件；
2. **交接物是文件，不是对话**。对话负责想清楚，文件负责传下去；
3. **从外部回来的话必须变成约束**，否则等于没回来。

## 5. 落地形态

```
本地执行（工具、文件、终端）
   │  平时自己跑，自己验，不推不动
   │
   ├─ 决策点 A：做到一定程度，看效果 ──▶ 材料：改动清单 + 效果证据
   ├─ 决策点 B：卡住了 ───────────────▶ 材料：报错原文 + 试过的动作 + 卡点
   └─ 决策点 C：不满意 ───────────────▶ 材料：你的原话 + 空白点（由接手方追问）
                    │
                    ▼
         外部顾问（网页 Chat 等）读取、判断、给意见
                    │
                    ▼
         意见单 → 人批准 → 约束变更单 → 回写
                    │
                    ▼
              下一轮按约束执行
```

关键约束：

- 执行者必须能**直接读写同一份权威文件**（同机或云端都行，物理位置不重要）；
- 决策点才交接，**平时不推**；
- 生成材料可以自动；**离开本地（上传、发布）必须单独授权**。

## 6. 被否掉的方案

| 方案 | 为什么不做 |
|---|---|
| chat-demo 做成右栏插件 | 它没有执行层，搬进去只是多一个聊天框 |
| 拆三层 agent 自动编排 | 成本高、收益是软的、交接依然难；每层都花 token，错误还会层层放大 |
| 每次执行都推 GitHub | 历史脏、噪音大、非代码产物无处放 |
| 云端执行解决一切 | 执行搬走了，文件没跟着走，反而多一道 push |
| 指望网页 chat 自动扫本地 | 浏览器沙箱不给后台扫盘权限，结构上不可能 |
| 先做「更深的思考层」 | 结果导向下不划算：**验得快 > 想得深** |
| 把结论写成「三行建议」 | 会越积越多互相打架，必须是带替代关系的变更单 |

## 7. 这套东西现在的样子

不是架构，是一个技能包：

```
SKILL.md                     流程规范：三态 / 三触发点 / 共同底座 / 回写 / 权限边界
ACCEPTANCE.md                这套东西自己的验收标准（自举）
references/acceptance-template.md   验收定义模板（自动栏 + 人工栏 + checks 围栏）
references/constraint-change.md     约束变更单
references/opinion-intake.md        意见单
scripts/check.mjs                   三态检查骨架
```

核心机制是**三态**：

| 状态 | 含义 | 退出码 |
|---|---|---|
| `PASS` | 跑过、确实对 | 0 |
| `FAIL` | 跑过、确实不对 | 1 |
| `UNVERIFIED` | 没跑 / 跑不了 / 还没实现 | **2** |

只要还有未验证项，整体退出码就是 2——**执行层拿不到假的完成信号**。

## 8. 已知缺口

| 缺口 | 状态 |
|---|---|
| 交接材料太重，小任务会烦 | 给了三档重量 + 轻量档判据，但仍未在真实小任务上验证 |
| 人工项的判断质量靠人自觉 | 已要求留证据（截图/日期/结论），但无法强制 |
| 「什么时候该交接」靠人判断 | 没有自动提醒，刻意不做（避免机械打断） |
| 工作流那一半（GitHub 当公告板、Chat 当顾问） | **不在文档里，靠用法**——文档只能给协议 |

## 9. 请验证的问题

如果你是来审这套东西的，请逐条回答，别泛泛评价：

1. **分层是否成立**：把「验收」和「交接」放在一起，是不是两个不相干的东西被硬凑？
2. **三态是否够用**：`UNVERIFIED` 会不会变成偷懒的出口——什么都写未验证，等于没验收？
3. **三触发点是否覆盖真实场景**：还有哪种情况需要交接但没被列进来？
4. **共同底座五项够不够**：目标、基线、相关文件、待决问题、自动验收——少了什么？
5. **约束变更单是否过重**：对小任务来说，「新增/替代/判定/readback」会不会没人愿意填？
6. **权限边界是否现实**：「只有人批准才能改标准」在真实协作里守得住吗？
7. **最可能死在哪**：如果这套东西三个月后没人用了，最可能的原因是什么？

第 7 题最重要。**不要夸它，直接说它会怎么死。**
