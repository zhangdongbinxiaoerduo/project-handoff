# 验收定义模板

把这份填成项目根目录的 `ACCEPTANCE.md`。目标是让"做完了"可判定，而不是靠感觉。

## 自动

能跑就是能跑，跑不了就老实写 `UNVERIFIED`。

| 编号 | 检查什么 | 怎么判 |
|---|---|---|
| A1 | 单元测试全绿 | 退出码 0 |
| A2 | 引用的文件都存在 | 无死链 |
| A3 | 页面无控制台报错 | `UNVERIFIED`（还没接无头浏览器） |

规则：

- 一项一行，编号固定（A1、A2……），**不写"等等"**；
- 未实现的写 `unverified`，不要留空——留空等于静默跳过；
- 一条检查命令只判一件事，判不了两件就拆开。

## 人工

自动化判不了、也不该假装能判的部分。**这部分必须由人看**。

| 编号 | 看什么 | 判据 | 留什么证据 |
|---|---|---|---|
| M1 | 交互生效（键位、按钮、暂停） | 你亲手点一遍 | 截图 + 日期 + 结论（过 / 不过） |
| M2 | 观感对不对（速度、节奏、手感） | 你看着舒服 | 一句话结论 + 日期 |
| M3 | 文案、措辞、语气 | 你认可 | 改前改后各一句 |
| M4 | 布局在不同尺寸下不塌 | 你拉窗口看 | 两张截图（最窄 / 最宽） |

判断也要留痕：**不是「我看过了」，而是「几号看过、结论是什么、证据在哪」。** 否则下一轮没人知道这条到底判过没有。

规则：

- 人工项**不许写成自动项**去糊弄（比如"截图存在"不等于"效果对"）；
- 每项给一个具体动作（点一遍 / 拉窗口 / 读一遍），别写"检查体验"。

## 机器可读部分

`scripts/check.mjs` 只读下面这个围栏，一行一项 JSON：

```checks
{"id":"A1","run":"node --test test/"}
{"id":"A2","run":"node scripts/check-links.mjs"}
{"id":"A3","unverified":"还没接无头浏览器"}
```

字段：

| 字段 | 含义 |
|---|---|
| `id` | 对应上表的编号 |
| `run` | 判据命令，退出码 0 即 PASS，非 0 即 FAIL |
| `unverified` | 写明为什么判不了，结果恒为 `UNVERIFIED`（退出码 2） |
| `cwd` | 可选，相对当前目录的执行位置 |

**没有 `run` 也没有 `unverified` 的项，一律 `UNVERIFIED`。**

## 三档重量

| 档 | 放什么 | 适合 |
|---|---|---|
| 轻量 | 只有 `ACCEPTANCE.md` | 单页面、玩具项目、一次性任务 |
| 标准 | + `constraints.md` | 会持续迭代的项目 |
| 完整 | + `docs/handoff/` | 有交接决策点的长期项目 |

**起始档位选低的，往上加容易，往下减麻烦。**

什么时候用轻量档（判据，别凭感觉）：

| 条件 | 轻量够用 |
|---|---|
| 任务不到半天 | ✅ |
| 只跑一次，不会再迭代 | ✅ |
| 没有第二个接手方 | ✅ |
| 有自动测试要跑 | ❌ 至少标准档 |
| 会换窗口继续做 | ❌ 上完整档 |

**流程压过工作，是这套东西最常见的死法。**
