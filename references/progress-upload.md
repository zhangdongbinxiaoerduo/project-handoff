# 进展上传格式

DSH 每次推到 GitHub 时写这一份。**只写事实，不写结论。**

Chat 端靠它 + 仓库里的真实文件来判断，所以路径必须能被 GitHub 打开。

## 格式

```
# 进展 <编号> · <日期>

基线：上一次上传 <commit 短号> / 首次上传

这次做了什么
- 一句话一件事，1~3 条

动了哪些文件
- path/to/file   （仓库路径，逐条列）

当前卡点
无
（或：具体一句，例如「build 在 Windows 上报 ENOENT，还没定位」）

下一步打算
- 一条，别写成计划书
```

## 规则

1. **不写结论**：不写「已完成」「通过」「没问题」，那是别人的判断；
2. **不写验收结果**：DSH 不负责判自己对不对；
3. **路径只写仓库路径**：`docs/progress/012.md` 可以，`E:\ds\x.md` 不行——Chat 打不开；
4. **卡点要么写「无」，要么写具体一句**：别写「还在调试」这种等于没说的；
5. **下一步一条**：写多了就变成计划书，而且下一轮一定要改。

## 编号

- 从 `001` 开始，递增；
- 文件名 `docs/progress/<编号>.md`；
- 与人工回写单的编号对应（`docs/reviews/<编号>.md`）。

## 反例（写了等于没写）

| 写法 | 问题 |
|---|---|
| 「已完成主要功能」 | 结论，不是事实 |
| 「改动了一些文件」 | 没路径，Chat 看不到 |
| 「测试通过」 | 自验，越权 |
| 「下一步：优化体验、补文档、加测试」 | 三条计划书，下一轮全要改 |

## 和回写单的关系

进展上传是**单向**的：DSH → 仓库 → Chat。

DSH 不读回写单去猜人的意思——回写单是给人看的，DSH 只按里面写明的约束执行，并且复述确认。
